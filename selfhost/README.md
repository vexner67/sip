# Sip на Sip

Компилятор Sip переписан на самом Sip и собирает сам себя без Python: нужен
только clang. Каждая часть выдаёт ровно то же, что эталон на Python в
`siplang/`: это проверяет `python3 selfhost/parity.py` (и тест `SelfhostTest`).

| Часть | Python | Sip | Статус |
|---|---|---|---|
| Лексер | `siplang/lexer.py` | `lexer.sip` | готов: токены, позиции и ошибки совпадают |
| Парсер | `siplang/parser.py` | `parser.sip` | готов: дерево и ошибки совпадают |
| Загрузчик модулей | `siplang/modules.py` | `modules.sip` | готов: `import`, `from ... import`, пакеты с `sip.toml` (зависимости-папки), std; git-зависимостей ещё нет |
| Проверка типов | `siplang/checker.py`, `siplang/types.py` | `checker.sip` | готова: типы всех выражений и ошибки совпадают |
| Типы в C | `siplang/cregistry.py` | `creg.sip` | готов: списки, словари, кортежи, записи, JSON, CSV |
| Генерация C | `siplang/cgen.py` | `cgen.sip` | готова: единицы C совпадают байт в байт |
| Сборка | `siplang/compiler.py` | `sipc.sip` | готова: кэш объектных файлов, clang параллельно, компоновка |
| Бэкенд arm64 | — | `arm64.sip`, `macho.sip`, `ngen.sip` | начат: `sipc native` без C и clang для int, bool, функций и циклов, с оптимизатором; не медленнее clang -O3; см. ниже |
| Рантайм | `siplang/native/sip_rt.h` | `siplang/std/rt.sip` | начат: строковые функции и `int(s)`; см. ниже |

## Сборка без Python

Python нужен один раз, чтобы получить первый `sipc`. Дальше `sipc` собирает
сам себя, и C у нового поколения совпадает с C предыдущего:

```bash
python3 -m siplang build selfhost/sipc.sip -o sipc   # первый раз, через Python
./sipc build selfhost/sipc.sip -o sipc               # дальше сам
./sipc run examples/greet.sip Ann
./sipc build examples/word_freq.sip -o wf
./sipc c examples/fib.sip                            # сгенерированный C
```

Стандартную библиотеку и рантайм `sipc` ищет в `--std DIR`, `$SIP_STD` или в
`siplang/std` в текущей папке, папке исходника или их родителях. Объектные
файлы лежат в `~/.cache/sip/obj` (или `$SIP_CACHE`), clang запускается
параллельно по единице на модуль, повторная сборка без правок не вызывает
clang. `sipc run` передаёт программе только позиционные аргументы; для флагов
`--name` соберите бинарник через `sipc build`.

Фронтенд на Sip быстрее Python: исходники самого компилятора (9.8 тысячи строк
с модулями и рантаймом на Sip) он проверяет и переводит в C за 0.09 с, Python за
0.69 с; маленькую программу — за 6 мс против 132 мс (из них около 3 мс — рантайм
на Sip, который подключается к каждой программе; clang компилирует его один раз
и дальше берёт из кэша). Сборка мусора занимает
около четверти этого времени: 3 сборки, 0.03 с (с `SIP_GC=off` — 0.066 с). Графики: [bench/charts.html](../bench/charts.html).

## Рантайм на Sip

Рантайм переехал из C (`siplang/native/sip_rt.h`) в Sip (`siplang/std/rt.sip`)
везде, где это логика, а не обращение к ОС: `sip_rt.h` сократился с 2267 до
1573 строк, `rt.sip` вырос до 1041. Загрузчик подключает `rt.sip` к каждой программе, как
модуль std с префиксом `std__rt__`; коду пользователя его имена не видны.
Генератор C вызывает его функции напрямую (`f_std__rt__str_replace(...)`). Перед
функциями, которые могут бросить ошибку, он ставит `sip_std_line`, поэтому
ошибка указывает на строку пользователя: `prog.sip:3: ParseError: invalid int: 'zz'`.
В раздельной сборке `rt.sip` — своя единица C, одна на все программы, и clang
компилирует её один раз.

На Sip написаны:

- строки: `lower`, `upper`, `isdigit`, `isalpha`, `isspace`, `isalnum`, `isupper`,
  `islower`, `capitalize`, `title`, `count`, `rfind`, `removeprefix`,
  `removesuffix`, `ljust`, `rjust`, `zfill`, `replace`, `strip`, `lstrip`,
  `rstrip`, `str * n`, `ord`, `chr` и `repr` строки;
- числа: `int(s)`, `float(s)` и печать float как в Python (кратчайшая запись,
  которая читается обратно);
- JSON и CSV целиком: лексер, строки с экранированием, числа, пути для ошибок
  (`$.users[0].age`), запись. Код под каждый тип по-прежнему генерирует
  компилятор, но он только вызывает функции `jp_*`, `je_*` и `csv_*` из `rt.sip`;
- разбор аргументов `fn main`: флаги, `--no-флаги`, позиционные, `*rest`, usage;
- перевод регулярных выражений в POSIX ERE (`std/re.sip`).

В C осталось ядро, которое Sip пока не выражает сам:

- примитивы для `rt.sip`: байт строки, кусок без копии, сырая память (`_alloc`,
  `_set`, `_fill`, `_copy`), построитель строк. Границы они не проверяют: их
  вызывает только `rt.sip`;
- то, что генератор вставляет прямо в код: арифметика с проверкой переполнения,
  сравнение, хэши, срезы и склейка строк, буфер `print`;
- сборщик мусора (нужен доступ к стеку и регистрам), ошибки на `setjmp`/`longjmp`
  с печатью при падении и запуском `sip test`, потоки и GIL для `async fn`;
- тонкие обёртки над libc и libcurl: файлы, `os`, время, `strtod`/`snprintf`,
  `regcomp`, HTTP.

Обёртки над libc на третьем этапе станут прямыми вызовами libSystem (так делает
и Go), а вставки генератора — машинными командами. Сборщику мусора и ошибкам
нужны чтение и запись памяти по адресу и доступ к кадру стека; их удобнее
переносить вместе со своим бэкендом, который даст эти примитивы.

По скорости функции на Sip не уступают прежним на C, а местами быстрее:

| | было (C) | стало (Sip) | Python |
|---|---|---|---|
| `json.read` 32 МБ в `[User]` | 80 мс | 48 мс | 179 мс |
| `json.stringify` того же | 547 мс | 147 мс | 142 мс |
| `csv.read` 500 тыс. строк в записи (без сборщика) | 27 мс | 28 мс | 395 мс |
| `csv.write` того же | 320 мс | 197 мс | 207 мс |

Вывод ускорился за счёт печати float: вместо перебора всех точностей (до 17
пар `snprintf` + `strtod` на число) берутся 15 значащих цифр без нулей в конце,
если они читаются обратно, иначе 16 или 17.

Функции на Sip Они написаны так, чтобы
clang мог их векторизовать: `c ^ 32` вместо `c + 32` и `sum(1 for ...)` для
подсчёта, потому что у этих операций нет проверки переполнения. `replace` и
`int(s)` стали быстрее (поиск подстроки теперь через `memchr`), остальные в
пределах шума; бенчмарки `bench/speed` не изменились.

## Свой бэкенд arm64 (без C)

`sipc native FILE.sip -o OUT` пишет исполняемый файл macOS arm64 сам: без C,
clang, ld и codesign. Проверенное дерево программы переводится прямо в машинный
код, файл Mach-O собирается и подписывается на Sip.

| файл | что делает |
|---|---|
| `arm64.sip` | ассемблер: кодировки команд, метки, поправки переходов и адресов (`b`, `b.cond`, `cbz`, `adr`, `adrp`) |
| `macho.sip` | Mach-O: сегменты `__TEXT`/`__DATA`/`__LINKEDIT`, импорт функций libSystem (`write`, `exit`, `mmap`, `memmove`, `memcmp`, `bzero`, `memchr`) через байткод dyld, ad-hoc подпись (CodeDirectory, SHA-256 каждой страницы, SHA-256 написан на Sip) |
| `ngen.sip` | генератор: переменные в x19..x28, промежуточные значения в x9..x15, буфер вывода 64 КБ и печать чисел на ассемблере |
| `../siplang/std/nrt.sip` | рантайм нативной сборки на Sip: куча и сборщик мусора, строки, списки; компилируется тем же `ngen` |

Поддерживаются:

- `int`, `bool`, функции до 8 аргументов, рекурсия, глобальные переменные;
- `if`/`elif`/`else`, `while`, `for x in a..b`, `break`/`continue`,
  `a, b = x, y`, `+= -= *=`;
- все целые операторы, сравнения (в том числе цепочки `a < b < c`),
  `and`/`or`/`not`, `abs`;
- **строки**: литералы, подстановки `"{x}"`, `+`, `len`, `s[i]`, срезы `s[a:b]`,
  сравнения, `in`, `for c in s`, `str(x)`, `find`, `startswith`, `endswith`,
  `sep.join(xs)`;
- **списки** любых из этих типов, в том числе вложенные: литералы, `[x] * n`,
  `+`, `len`, `l[i]` и `l[i] = v` (и `l[i] += v`), срезы, `append`, `pop()`,
  `in`, `for x in l`;
- **кортежи**: литералы, `t[0]`, распаковка `a, b = f()` и `for a, b in pairs`;
- **record** (`type Point(x int, y int = 0)`, без параметров типа): конструктор со
  значениями по умолчанию, чтение и запись полей (`p.x`, `.x += d`), методы,
  рекурсивные типы (`Tree(val int, kids [Tree])`);
- `==`, `!=` для списков, кортежей и record (по содержимому), `<`... для списков
  и кортежей (по элементам), `in` для списков любых из этих типов;
- `print` и `str` всего этого как в C-бэкенде (`['a', "b'c"]`, `Point(x=1, y=0)`, `(1,)`).

Ошибки времени выполнения те же, что у C-бэкенда: переполнение —
`OverflowError`, `//` и `%` округляют вниз и падают на нуле, индекс вне
строки или списка и `pop` из пустого — `IndexError`, функция без `return` —
`Error`. Текст (файл:строка, вид, строка исходника) и код выхода совпадают.
Остальное (float, словари, множества, `T?`, варианты, интерфейсы, лямбды,
модули std) пока даёт
ошибку компиляции `native backend: ... not supported yet`. Тест `NativeTest`
сравнивает вывод, ошибки и код выхода с C-бэкендом.

### Память

Строка и список — адрес объекта в одном регистре. Строка — `[длина][байты]`,
литералы лежат в `__TEXT`, строки из одного байта — готовая таблица на 256
строк, поэтому `s[i]` и `for c in s` память не выделяют. Список —
`[n][cap][данные]`, данные отдельным объектом по 8 байт на элемент. Кортеж и
record — объект по слову на поле.

Печать, `==` и `<` для составных типов — обобщённые функции рантайма. Им
передаётся вид значения: 0 — int, 1 — bool, 2 — str, иначе смещение описателя
типа в `__const`. Описатель списка — вид элемента, кортежа — виды полей, record —
имя, имена и виды полей. Генератор строит описатели сам, по одному на тип.

Рантайм (`std/nrt.sip`) написан на Sip. Указатели в нём — обычные `int`, память
читается и пишется встроенными функциями (`_ld`, `_st`, ...), которые генератор
превращает в отдельные команды `ldr`/`str`. Код рантайма компилируется без
проверок переполнения. `alloc` листовая: блок берётся из списка свободных нужного
размера или сдвигом границы, а редкий путь — хвостовой переход в `_alloc_slow`.

Сборщик мусора консервативный, mark-sweep, без перемещения. Корни — стек,
регистры x19..x28 (их сохраняет в стек короткая подпрограмма перед сборкой) и
`__bss`. Слово считается ссылкой, если указывает ровно на данные выделенного
блока; это проверяется по карте начал блоков (байт на 16 байт кучи). Соседние
мёртвые блоки при сборке сливаются, мёртвый хвост кучи возвращается под
выделение сдвигом. Сборка запускается, когда после прошлой выделено больше
max(32 МБ, живой объём). Куча — 16 ГБ зарезервированных адресов, система даёт
память по мере касания.

### Оптимизатор

Генератор сам оптимизирует код, без промежуточного представления и отдельных
проходов по нему:

- **Точный кадр.** Функция генерируется дважды. Пробный проход узнаёт, есть ли
  вызовы и сколько сохраняемых регистров нужно. Чистовой пишет `stp`/`ldp`
  только этих регистров, а эпилог ставит прямо в каждый `return`. Листовая
  функция держит переменные в x0..x8: параметры остаются, где пришли, кадра нет.
- **Значения через вызов** живут в сохраняемых регистрах x19..x28, а не в памяти.
  Глобальные переменные, которых не касается ни одна функция, живут в регистрах
  верхнего уровня.
- **Диапазоны.**
  - Из условий выводятся факты: после `if n < 2 then return n` известно `n >= 2`.
  - Каждой изменяемой переменной вычисляется диапазон: объединение по всем
    присваиваниям, до неподвижной точки, с расширением до всего int. После
    `x = (...) & 2147483647` известно, что `x` лежит в `[0, 2**31)`.
  - Проверка переполнения ставится, только если оно возможно. `//` и `%` без
    поправки округления — когда делимое заведомо неотрицательно.
- **Встраивание** функций вида `fn f(x) = выражение`, рекурсивных на один
  уровень. Константные аргументы подставляются и сворачиваются.
- **Мелочи:**
  - `//` и `%` на степень двойки — `asr` и маска; на другую константу при
    неотрицательном делимом — умножение на магическое число (`umulh`, `lsr`)
    вместо `sdiv`; `x % y == 0` — без поправки, для `% 2` через `tbz`;
  - умножение на степень двойки — сдвиг (с проверкой переполнения обратным сдвигом);
  - `return f(...)` — хвостовой переход: функция без других вызовов остаётся
    листовой, хвостовая рекурсия не растит стек;
  - факты из `!=` на краю диапазона: после `if x == INT_MIN then return` известно,
    что `-x` не переполнится; в ветках `if c then a else b` известно `c`;
  - склейка строк (`"{w}-{i}"`, `a + str(n) + b`) — одно выделение памяти на всё
    выражение, числа пишутся цифрами сразу в результат;
  - делитель `-1` вынесен в холодный хвост функции;
  - умножение на 2..5 — сложениями; `mul` + `add` → `madd`;
  - большие константы вынесены из циклов в регистры;
  - `for` — три команды на виток (`cmp`, `add`, `b.lt`);
  - результат последней команды сразу пишется в регистр переменной;
  - `a, b = b, a % b` — параллельная пересылка.

Каждая оптимизация сохраняет поведение C-бэкенда, включая место и текст
ошибки. Тесты `NativeTest` сравнивают вывод, ошибки и код выхода на программах
с переполнениями, делением при всех знаках и перестановками.

Скорость против C-бэкенда (clang -O3), лучшее из 5 запусков, Apple M-серии
(`python3 bench/native/run.py`):

| программа | что нагружает | native | C | C / native |
|---|---|---|---|---|
| `fib` | рекурсия | 67 мс | 85 мс | 1.28× |
| `primes` | деление | 118 мс | 125 мс | 1.05× |
| `loops` | умножение, побитовые операции | 352 мс | 358 мс | 1.02× |
| `collatz` | ветвления, деление на 2 | 300 мс | 302 мс | 1.01× |
| `gcd` | остаток в цикле | 175 мс | 175 мс | 1.00× |
| `lists` | append, индексы, срезы, вложенные списки | 15 мс | 14 мс | 0.93× |
| `strings` | подстановки, срезы, поиск, сравнение строк | 135 мс | 62 мс | 0.46× |

На циклах обе версии упираются в задержку цепочки зависимостей (например,
`madd → and` в `loops`), так что разница в пределах шума. fib быстрее за счёт
встраивания одного уровня рекурсии. Компиляция занимает около 7 мс против
~140 мс у clang без кэша.

Clang всё ещё лучше в двух вещах: он встраивает функции с циклами (у нас
встраиваются только функции-выражения) и знает теорию чисел (например, что
`3 * x + 1` не переполняется, если не переполнилось `3 * x`). На строках C
пока вдвое быстрее по той же причине: его рантайм встраивается в место вызова,
а у нас каждая операция — несколько вызовов функций рантайма со своими кадрами.

## Команды

```bash
sip run selfhost/lexer.sip FILE.sip    # токены построчно
sip run selfhost/parser.sip FILE.sip   # дерево, узел на строку
sip run selfhost/checker.sip FILE.sip  # дерево с типом каждого выражения или первая ошибка
sip run selfhost/cgen.sip FILE.sip     # единицы C, как их выдаёт siplang/cgen.py
python3 selfhost/parity.py             # сравнение с Python на всех .sip репозитория
python3 selfhost/parity.py --corpus    # собрать программы из набора тестов (~/.cache/sip/selfhost-corpus)
python3 selfhost/parity.py --only checker
python3 selfhost/parity.py --only cgen
```

Проверку типов (вместе с загрузкой модулей) сравнивает тот же `parity.py`: обе
стороны печатают дерево всей программы после проверки, и у каждого выражения
стоит его тип (`Name@3 :: [int]`), либо выводят первую ошибку. Входы: файлы
репозитория, трудные случаи и проекты из нескольких файлов из `parity.py`
(циклический импорт, приватные имена, пакеты, обобщённые типы из модуля, ошибки
в импортированном файле) и программы, которые компилирует набор тестов (среди
них много программ с ошибками типов).

`checker.sip` проверяет сам себя вместе с `modules.sip`, `parser.sip`, `lexer.sip`
и модулями std `os` и `path`: дерево с типами (около 77 тысяч строк) совпадает с
Python, и получается оно примерно в 8 раз быстрее.

В `sip.toml` загрузчик понимает `[package] name` и `[deps]` вида
`kit = "../kit"` или `kit = { path = "../kit" }`; `[c] flags` нужны только
компилятору C. Для git-зависимостей пока есть только сообщение об ошибке.

Дерево в `parser.sip` — один общий узел `N(kind, line, s, kids, ty)`: `kind` — имя
класса из `siplang/nodes.py`, дети идут в порядке его полей. Листья: строка
(`str`), `None`, `bool`, список (`list`) и кортеж (`tuple`). Поля extern-функций
лежат в дополнительном ребёнке `extern`.

`ty` — номер типа узла в таблице проверки типов. Типы в `checker.sip` — тоже один
вид `Ty` с полем `k` (prim, list, tvar, record, ...); тождество объектов Python
заменено номером `id`.

Лексер и парсер разбирают сами себя и весь код репозитория, включая стандартную библиотеку.
